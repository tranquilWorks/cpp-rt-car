## Review, rollback and limits

Review covers copied-job publication/reuse, exactly-once accepted work, scratch
borrowing, nested helper progress, control-thread registration, host quiescence
beyond Runtime completion, provider acquisition/apply/rollback/release, configuring
versus started cleanup, monotonic frame admission and bounded telemetry ownership.
No unresolved implementation finding remains; no production change is required. Provider observation uses actual OS readback
because the public provider contract requires independent observation; it does
not fabricate that capability from a copied apply result. Startup and cleanup
remain control-plane operations. Final validation remains required.

A pool has one registered frame-control thread and supports at most two attached
Runtime owners. Callers join external submissions before lifecycle changes.
An accepted arbitrary job that never returns cannot be made safe by forced free;
this reference retains owners on failed quiescence. Worker joining has ordinary
OS scheduling dependence. A callback error can leave partial application state;
this example stops admission rather than claiming rollback. Residency is only a
snapshot, not locking or physical qualification. The provider replaces three
resident regions, not all Runtime/host heap or stack allocations. No complete
memory-accounting claim is made. Independent novice first-use is unperformed.

Rollback is a scoped revert of additive host source/tests/docs and package wiring.
Preserve Runtime/backends, public SDK/ABI, all previous repairs and evidence.
Remaining software after this batch: M25-06 installed API/docs/recipes and six M26
full-system batches. Hardware/RT1/RT2, controlled performance, Unreal and signing/
release/deployment remain separate and unperformed here.
