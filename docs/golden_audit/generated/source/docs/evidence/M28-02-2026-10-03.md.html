## Cause and correction

The unchanged historical runner passes1000 ordinary invocations. Its held-submit
control retains the original1ms deadline, one provider call, one timeout terminal
and no copied output, but observes zero backend submissions and fails the original
exact-one-submission predicate. Raw exit1 and diagnostic are retained. The same new
before-acceptance control also rejects the unchanged provider and passes the repair.
This proves a scheduling assumption; the exact cause of the historical hosted
M26-03/M23 benchmark failure remains unproven and its evidence is unchanged.

The provider retains exact terminal status/count, sampled nonpublication and
callback/state checks. It records backend submissions at the terminal as a lower
bound, then successfully stops the Runtime before checking stable final accounting.
There must be exactly one observed submit attempt. The valid final states are:

| Terminal to settled acceptance | Submit return | Final device work |
| --- | --- | --- |
| 0 to0, timeout only | invalid_state after stop closed admission | zero copies/actions/completions/cancellations/rejections |
| 0 or1 to1, timeout | ok | one copy/action; either no successful cancellation/completion or exactly one of each |
| 1 to1, injected completion error | ok | one copy/action/completion, no cancellation |

Every state also requires unchanged sampled output and copied application state,
zero Runtime outstanding work after checked stop, and no backend queue rejection.
No observer storage or borrowed Runtime/backend/clock/buffer lifetime ends early.

Initialized TSan of the first candidate exposed a pre-existing loopback backend
race: cancel reads completion storage before submit publishes its writes for a
held timeout. The same held-after-acceptance control independently reproduces that
race against unchanged device.cpp (initialized attempt46). Canonical amendment611
permits a fixture-owned observer only for failure/timeout cases. It publishes
submit's returned status with release ordering, and forwards cancellation only
following an acquire observation of acceptance. Before acceptance, cancellation
returns invalid_argument and ownership stays with checked shutdown. It adds no
callback mutex, retry loop, allocation, thread, or Runtime/backend modification.
Other benchmark workloads and existing source/public schemas remain unchanged.

This corrects the provider's use of the backend, not every direct backend caller.
The broader loopback cancel/submit storage race remains an unresolved software
finding for later M28 closeout triage; no global backend qualification is claimed.
